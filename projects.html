Progetto 01 — Enterprise

Asgard

Piattaforma di microservizi per la digitalizzazione aziendale

Progetto Aziendale Uso Interno Microservizi
NestJS Angular NgRx TypeScript MongoDB RabbitMQ NATS Docker JWT Microsoft Entra ID Azure Container Apps Azure DevOps PrimeNG Mongoose

Asgard è una piattaforma enterprise modulare basata su architettura a microservizi che fornisce un ecosistema completo per la digitalizzazione aziendale. Il sistema integra gestione identità (IAM), workflow dinamici, ticketing, gestione documentale, inventario IT e IPAM, notifiche e servizi di ricerca aggregata. Il backend è sviluppato con NestJS in modalità monorepo, mentre il frontend è un'applicazione Angular standalone con gestione dello stato tramite NgRx.

Nota: Asgard è un progetto ad uso interno attualmente in corso di sviluppo. Alcuni dettagli implementativi e configurazioni infrastrutturali sono omessi per ragioni di riservatezza.

Architettura a 10 Microservizi

Il sistema è composto da 10 microservizi specializzati, ognuno responsabile di un dominio specifico. Ogni servizio ha il proprio database MongoDB dedicato per garantire isolamento e scalabilità indipendente.

La comunicazione tra servizi avviene su due canali: HTTP REST per le chiamate sincrone (es. ricerca aggregata, verifica destinatari) e RabbitMQ/NATS per il messaging asincrono (es. logging centralizzato, invio notifiche email). Il pattern ClientProxy di NestJS gestisce entrambi i protocolli in modo trasparente.

Comunicazione inter-servizio

Ogni microservizio si connette ai bus di messaggistica tramite il sistema di microservices nativo di NestJS. Il pattern fire-and-forget (emit) viene usato per logging e notifiche, mentre il pattern request/response (send) per operazioni che richiedono una risposta, come la verifica dei destinatari di un ticket.

Backend — NestJS Monorepo

Il backend è strutturato come un monorepo NestJS che contiene tutti i 10 microservizi sotto la directory apps/ e un set di librerie condivise in libs/. Le librerie forniscono infrastruttura trasversale: configurazione JWT, guard per autenticazione e autorizzazione, decoratori custom, definizione dei permessi e pipe di validazione.

Ogni servizio espone i propri endpoint REST e si registra contemporaneamente come microservizio RabbitMQ e NATS. Il sistema di permessi è granulare, con autorizzazioni specifiche per ognuna delle 16+ risorse gestite (ticket, news, FAQ, workflow, richieste, asset, IP, subnet, VLAN, rack, ecc.).

Schema Ticket — Mongoose

I ticket sono il cuore del sistema di supporto. Lo schema Mongoose utilizza decoratori @Prop con validazioni enum per stati e priorità, e definisce indici ottimizzati sulle query più frequenti: ricerca per destinatario, operatore attivo, categoria e data di creazione.

Ogni ticket attraversa un ciclo di vita: Nuovo → In carico → In attesa → Risolto, con quattro livelli di priorità (Bassa, Media, Alta, Urgente) e assegnazione a utenti, gruppi o organizzazioni.

Creazione di un Ticket

Quando un utente crea un ticket, il servizio Atlas arricchisce i dati con le informazioni dell'autore estratte dal JWT, persiste il documento in MongoDB, registra l'azione nel logger centralizzato Bravon tramite RabbitMQ e invia una notifica email via Deltor con template Handlebars personalizzato.

Questo flusso illustra la collaborazione tra microservizi: un singolo endpoint REST in Atlas scatena eventi su due servizi distinti (logging e notifiche) in modo completamente asincrono.

tickets/tickets.service.ts — create() 
async create(
  createTicketDto: CreateTicketDto,
  user: ActiveUserData,
): Promise<Ticket> {
  const author = {
    fullname: user.fullname,
    sub: user.sub,
    email: user.email,
    location: user.location,
  };

  const createdTicket = new this.ticketModel({
    ...createTicketDto,
    creationDate: new Date(),
    user: author,
  });

  await createdTicket.save();

  // Log su Bravon (RabbitMQ fire-and-forget)
  await this.logAction(
    'ticket.create',
    `Ticket: ${createTicketDto.subject}`
  );

  // Notifica via Deltor (template Handlebars)
  await this.sendEmailNotification({
    subject: `Nuovo Ticket - ${createTicketDto.subject}`,
    template: 'ticket-created',
    additionalData: {
      ticketSubject: createTicketDto.subject,
      authorName: user.fullname,
      category: createTicketDto.category,
      priority: createTicketDto.priority,
    },
  });

  return createdTicket;
}

Assegnazione transazionale

L'assegnazione di un ticket a un operatore utilizza le transazioni MongoDB per garantire consistenza atomica: il sistema verifica che l'operatore non abbia già un ticket attivo e che il ticket non sia già assegnato, il tutto all'interno di una singola sessione transazionale.

In caso di errore o violazione dei vincoli, l'intera operazione viene annullata tramite abortTransaction(), prevenendo assegnazioni duplicate o stati inconsistenti.

tickets/tickets.service.ts — assignTicketToOperator() 
async assignTicketToOperator(
  ticketId: string,
  operator: Partial<ActiveUserData>,
): Promise<HttpStatus> {
  const session = await this.ticketModel
    .startSession();
  session.startTransaction();

  try {
    // Verifica vincoli di business
    await this.checkOperatorHasAssignedTicket(
      operator
    );
    const ticket = await this
      .checkTicketIsNotAssigned(ticketId);

    ticket.operator = {
      fullname: operator.fullname,
      sub: operator.sub,
      email: operator.email,
    };
    ticket.active = true;
    await ticket.save({ session });

    await session.commitTransaction();
    return HttpStatus.OK;
  } catch (error) {
    await session.abortTransaction();
    throw error;
  } finally {
    session.endSession();
  }
}

Workflow e richieste — Gravos

Gravos implementa un motore di workflow configurabile. Ogni workflow definisce dei campi dinamici (stringa, numero, email, data, booleano, array con opzioni) e una pipeline di step di approvazione con tre modalità:

  • SEQUENTIAL — Gli approvatori devono approvare in ordine.
  • PARALLEL — Approvazioni parallele con soglia minima configurabile.
  • DYNAMIC — Approvatore risolto a runtime in base al ruolo (responsabile del richiedente o coordinatore del gruppo).

Motore di approvazione multi-step

Il cuore di Gravos è il metodo approveRequest: verifica l'autorizzazione dell'utente sullo step corrente, previene doppie approvazioni, determina se lo step è completato e avanza la richiesta attraverso la pipeline. Lo stato segue il flusso: PENDING → IN_PROGRESS → APPROVED/REJECTED → COMPLETED.

requests/requests.service.ts — approveRequest() 
async approveRequest(
  id: string,
  approvalDto: ApprovalRecordDto,
  user: ActiveUserData,
): Promise<Request> {
  const request = await this.requestModel
    .findById(id);
  const workflow = await this.workflowsService
    .findOne(request.workflowId, user);
  const currentStep =
    workflow.steps[request.currentStepIndex];

  // Verifica autorizzazione e doppia approvazione
  const canApprove = await this
    .canUserApproveStep(currentStep, user, request);
  if (!canApprove) throw new BadRequestException(
    'Non autorizzato per questo step'
  );

  // Registra approvazione e avanza pipeline
  request.approvals.push({
    stepIndex: request.currentStepIndex,
    userId: user.sub, approved: approvalDto.approved,
    timestamp: new Date(),
  });

  const completed = this
    .isStepCompleted(currentStep, request);
  const approved = this
    .isStepApproved(currentStep, request);

  if (completed && approved) {
    if (request.currentStepIndex
        < workflow.steps.length - 1) {
      request.currentStepIndex += 1;
      request.status = 'IN_PROGRESS';
    } else {
      request.status = 'APPROVED';
    }
  }

  return await request.save();
}

Ricerca aggregata cross-service

Il servizio Asgard (gateway) orchestra una ricerca federata in parallelo interrogando simultaneamente FAQ (Elios), News (Corvin), Categorie ticket (Atlas) e Workflow (Gravos) tramite Promise.allSettled. I risultati vengono aggregati, ordinati per relevance e arricchiti con suggerimenti contestuali.

Se cerchi "permesso ferie", il sistema non solo trova FAQ e news correlate, ma suggerisce automaticamente di creare un ticket HR o avviare una richiesta ferie.

search/search.service.ts — performIntelligentSearch() 
async performIntelligentSearch(
  searchQuery: SearchQueryDto,
): Promise<SearchResponseDto> {
  const startTime = Date.now();
  const { query } = searchQuery;

  // Ricerche parallele su 4 microservizi
  const [faqs, news, categories, workflows] =
    await Promise.allSettled([
      this.searchFAQs(query),
      this.searchNews(query),
      this.getRelevantCategories(query),
      this.searchWorkflows(query),
    ]);

  // Aggrega e ordina per rilevanza
  const quickActions: QuickAction[] = [];
  if (faqs.status === 'fulfilled')
    quickActions.push(
      ...this.mapFAQsToActions(faqs.value)
    );
  if (news.status === 'fulfilled')
    quickActions.push(
      ...this.mapNewsToActions(news.value)
    );

  quickActions.sort(
    (a, b) => b.relevance - a.relevance
  );

  return {
    query,
    quickActions: quickActions.slice(0, 10),
    ticketSuggestions: this
      .generateTicketSuggestions(categories),
    requestSuggestions: this
      .generateRequestSuggestions(workflows),
    processingTime: Date.now() - startTime,
  };
}

SSO — Microsoft Entra ID

L'autenticazione aziendale è gestita da Heimdall attraverso Microsoft Entra ID (ex Azure AD) come SSO aziendale, implementando il flusso completo OAuth2/OIDC con PKCE. Il sistema supporta anche l'autenticazione tramite CIE (Carta d'Identità Elettronica), identificando l'utente tramite codice fiscale.

La validazione dell'ID Token include verifica della firma JWKS, controllo issuer/audience, scadenza e protezione contro replay attack tramite nonce. Dopo la validazione, il sistema genera token JWT interni con permessi granulari, gruppi e organizzazione dell'utente.

authentication/authentication.service.ts 
async exchangeOAuthCode(
  codeExchangeDto: OAuthCodeExchangeDto,
): Promise<MicrosoftAuthResponse> {
  // 1. Validazione state (CSRF protection)
  this.validateState(codeExchangeDto.state);

  // 2. Scambio code → token con Microsoft
  const msTokens = await this
    .exchangeCodeForToken(
      codeExchangeDto.code,
      codeExchangeDto.codeVerifier,
      codeExchangeDto.redirectUri,
    );

  // 3. Validazione ID Token (JWKS + nonce)
  const claims = await this
    .validateIdToken(
      msTokens.id_token,
      codeExchangeDto.nonce,
    );

  // 4. Informazioni utente da Microsoft Graph
  const userInfo = await this
    .getMicrosoftUserInfo(msTokens.access_token);

  // 5. Lookup utente interno + populate gruppi
  let user = await this.userModel
    .findOne({ email: claims.email })
    .populate({
      path: 'groups',
      populate: { path: 'organization' },
    });

  // 6. Generazione token JWT interni
  const tokens = await this
    .generateTokens(user._id, {
      email: user.email,
      permissions: user.permissions,
      fullname: user.fullName,
      groups: user.groups.map(g => g._id),
      organization: user.groups[0]?.organization,
    });

  return { ...tokens, entraUserInfo: userInfo };
}

Validazione ID Token — JWKS

La validazione del token Microsoft segue le best practice OIDC: la libreria jose scarica le chiavi pubbliche dal JWKS endpoint di Microsoft, verifica la firma, controlla issuer e audience, e valida il nonce per prevenire attacchi di tipo replay.

authentication/authentication.service.ts — validateIdToken() 
private async validateIdToken(
  idToken: string,
  expectedNonce?: string,
): Promise<IdTokenClaims> {
  const JWKS = jose.createRemoteJWKSet(
    new URL(this.MICROSOFT_JWKS_URI)
  );

  const { payload } = await jose.jwtVerify(
    idToken, JWKS, {
      issuer: this.MICROSOFT_ISSUER,
      audience: this.MICROSOFT_CLIENT_ID,
    }
  );

  const claims = payload as IdTokenClaims;

  // Protezione contro replay attack
  if (expectedNonce && claims.nonce !== expectedNonce)
    throw new UnauthorizedException(
      'Nonce validation failed'
    );

  return claims;
}

Frontend — Angular + NgRx

Il frontend è un'applicazione Angular 21 basata interamente su standalone components (nessun NgModule). La gestione dello stato è centralizzata tramite NgRx con 17 feature slice nello store, corrispondenti ai diversi domini dell'applicazione. L'interfaccia utilizza PrimeNG con un tema custom (AtlasPreset), Leaflet per le mappe, Chart.js per i grafici e Quill come rich text editor.

Ogni feature segue una struttura consistente: dentro state/ si trovano actions, reducer, effects, selectors e model. Questo pattern garantisce separazione delle responsabilità, testabilità e prevedibilità del flusso dati unidirezionale.

Actions e Reducer — Pattern NgRx

Ogni entità segue il pattern Command/Success/Failure: l'action di comando viene dispatched dal componente, l'effect gestisce la chiamata API, e le action di successo/errore aggiornano il reducer. Lo stato traccia il loading per ogni operazione individualmente.

Il reducer dei ticket usa una Map per deduplicare i risultati durante lo scroll infinito, evitando duplicati quando nuovi dati vengono accumulati progressivamente.

atlas/state/ticket.actions.ts + ticket.reducer.ts 
// ─── Actions (tripletta Command/Success/Failure)
export const getAllTickets = createAction(
  '[Ticket] Get All'
);
export const getAllTicketsSuccess = createAction(
  '[Ticket] Get All Success',
  props<{ total: number; tickets: Ticket[] }>()
);
export const createTicket = createAction(
  '[Ticket] Create',
  props<{ ticket: CreateTicketDto }>()
);
export const assignTicket = createAction(
  '[Ticket] Assign',
  props<{ id: string }>()
);

// ─── Reducer con Map per deduplicazione
export const ticketReducer = createReducer(
  initialState,
  on(getAllTicketsSuccess, (state, { total, tickets }) => {
    const map = new Map(
      state.allTickets.map(t => [t._id, t])
    );
    tickets.forEach(t => map.set(t._id, t));
    return {
      ...state,
      allTickets: Array.from(map.values()),
      loadingAllTickets: { loading: false, error: null },
      pagination: { ...state.pagination, total,
        hasMore: tickets.length === state.pagination.limit },
    };
  }),
  on(setFilters, (state, { filters }) => ({
    ...state, filters, allTickets: [],
    pagination: { ...state.pagination, skip: 0 },
  })),
);

Effects — Side Effects & API Calls

Gli Effects gestiscono ogni interazione con il backend. Utilizzano exhaustMap per le chiamate API, withLatestFrom per leggere lo stato corrente (paginazione e filtri), retry per resilienza automatica e tap per side effect come toast e navigazione.

Il pattern è consistente in tutti i 17 slice: l'effect si sottoscrive all'action, legge i parametri dallo store, chiama il service HTTP e dispatcha l'action di successo o errore.

atlas/state/ticket.effects.ts 
@Injectable()
export class TicketEffects {
  private actions = inject(Actions);
  private store = inject(Store);
  private ticketService = inject(TicketService);
  private messageService = inject(MessageService);

  getAllTickets = createEffect(() =>
    this.actions.pipe(
      ofType(getAllTickets, setFilters),
      withLatestFrom(
        this.store.pipe(select(selectLimit)),
        this.store.pipe(select(selectSkip)),
        this.store.pipe(select(selectFilter))
      ),
      exhaustMap(([, limit, skip, filters]) =>
        this.ticketService
          .getAllTickets(limit, skip, filters).pipe(
            retry({ count: 4, delay: 4000 }),
            map(({ total, tickets }) =>
              getAllTicketsSuccess({ total, tickets })
            ),
            catchError(err =>
              of(getAllTicketsFailure({ error: err }))
            )
          )
      )
    )
  );

  createTicketSuccess = createEffect(() =>
    this.actions.pipe(
      ofType(createTicketSuccess),
      tap(({ id }) => {
        this.messageService.add({
          key: 'global-toast',
          severity: 'success',
          summary: 'Successo',
          detail: 'Ticket creato con successo!',
        });
        this.router.navigate(
          ['/atlas/create-ticket/end', id]
        );
      })
    ), { dispatch: false }
  );
}

Cloud & DevOps — Azure

L'infrastruttura di Asgard è interamente basata sull'ecosistema Microsoft Azure:

  • Azure Container Apps — Ogni microservizio viene deployato come container isolato su Azure Container Apps, beneficiando di scaling automatico, revisioni e ingress management senza la complessità di Kubernetes.
  • Azure Container Registry (ACR) — Le immagini Docker di tutti i servizi (backend e frontend) vengono costruite e pubblicate in un registry privato ACR, garantendo sicurezza e velocità di pull durante il deployment.
  • Azure DevOps — Le pipeline CI/CD sono definite in azure-pipelines.yml e gestiscono build, test, creazione immagini Docker e deployment automatico su Container Apps. Ogni push sul branch principale attiva l'intera pipeline.
  • Microsoft Entra ID — Utilizzato come identity provider aziendale per il Single Sign-On (SSO) tramite il protocollo OAuth2/OIDC con PKCE, integrato nativamente nel flusso di autenticazione di Heimdall.

Sistema di Guard e Permessi

Ogni endpoint è protetto da un sistema a due livelli di guard globali registrati come APP_GUARD: il primo verifica l'autenticazione (JWT access token, skip per endpoint pubblici), il secondo controlla i permessi granulari per le 16+ risorse del sistema.

I decoratori custom @Auth(), @Permissions() e @ActiveUser() semplificano l'uso nei controller, rendendo la sicurezza dichiarativa e consistente in tutto il monorepo.

Architettura di sicurezza 
// Guard globali registrati in ogni servizio
providers: [
  { provide: APP_GUARD,
    useClass: AuthenticationGuard },
  { provide: APP_GUARD,
    useClass: PermissionsGuard },
],

// Uso nei controller con decoratori custom
@Permissions(
  Permission.TicketCreate,
  Permission.TicketAll
)
@Post()
async create(
  @Body() dto: CreateTicketDto,
  @ActiveUser() user: ActiveUserData,
) {
  return this.ticketsService.create(dto, user);
}

// Endpoint pubblico (nessuna autenticazione)
@Auth(AuthType.None)
@Get('public')
async getPublicFaqs() {
  return this.faqsService.findPublic();
}

Scheduler e task automatici

Atlas utilizza il modulo @nestjs/schedule per eseguire task automatici tramite espressioni Cron. Lo scheduler sblocca automaticamente i ticket rimasti inattivi per oltre un'ora e esegue un cleanup giornaliero dei ticket attivi, garantendo che nessuna richiesta rimanga bloccata per disattenzione.

Stato del progetto

Asgard è un progetto in sviluppo attivo, continuamente esteso con nuove funzionalità e moduli. L'architettura a microservizi consente di aggiungere nuovi servizi senza impattare quelli esistenti, e il monorepo NestJS facilita la condivisione di codice tra i servizi tramite le librerie in libs/.

Nota: essendo un progetto ad uso aziendale interno, le configurazioni infrastrutturali, le variabili d'ambiente, gli endpoint specifici e altri dettagli sensibili sono stati omessi da questa presentazione per ragioni di riservatezza.

Progetto 02 — Accademico

Token Ring Banking System

Mutua esclusione distribuita con elezione del coordinatore

Progetto Universitario Sistemi Distribuiti
NestJS TypeScript Axios RxJS UUID Jest

Progetto per il corso di Intelligenza Artificiale Distribuita. Implementa un sistema bancario distribuito con 4 nodi ATM indipendenti che condividono l'accesso a un saldo comune senza memoria condivisa — tutta la coordinazione avviene tramite message passing HTTP.

L'algoritmo Token Ring garantisce la mutua esclusione: un singolo token circola nel ring e porta con sé il saldo. Solo il nodo che possiede il token può eseguire transazioni. Il Bully Algorithm gestisce l'elezione del coordinatore in caso di guasti.

Architettura del Ring

4 processi NestJS indipendenti (ATM1–ATM4) su porte 3001–3004, disposti in un anello logico. Il token circola in una sola direzione e trasporta il saldo corrente del conto bancario.

Nessuna memoria condivisa: il saldo vive esclusivamente nel token. Quando un nodo riceve il token, può eseguire una transazione (deposito/prelievo) e poi lo inoltra al nodo successivo.

Il cuore del Token Ring

Il token è una struttura semplice: un ID univoco (UUID), l'ID del nodo che lo detiene e il saldo corrente. Quando un nodo lo riceve, controlla se ha transazioni in coda: se sì, entra nella sezione critica ed esegue; altrimenti, inoltra immediatamente.

Questa è la garanzia fondamentale della mutua esclusione: un solo nodo alla volta può modificare il saldo, eliminando race condition senza lock o semafori.

common/types.ts 
export interface Token {
  id: string;       // UUID univoco
  holderId: number;  // Nodo corrente
  balance: number;   // Saldo del conto
}

Sezione critica

processToken() è il cuore dell'algoritmo. Quando arriva il token, se ci sono transazioni in coda il nodo entra nella sezione critica, esegue la transazione, aggiorna il saldo nel token e lo inoltra al prossimo nodo.

Il servizio BankingService è stateless: riceve il saldo corrente e restituisce il nuovo saldo, senza mantenere stato locale. Questo riflette il principio che il saldo vive esclusivamente nel token.

atm/atm.service.ts 
private async processToken(): Promise<void> {
  this.isProcessing = true;
  try {
    if (this.tokenService.canAccessCriticalSection()) {
      // Ha transazioni in coda: esegui
      await this.executeNextTransaction();
    } else {
      // Nessuna transazione: inoltra
      await this.forwardToken();
    }
  } finally {
    this.isProcessing = false;
  }
}

Bully Algorithm

Quando un nodo rileva un guasto, avvia un'elezione: invia un messaggio ELECTION a tutti i nodi con ID superiore. Se nessuno risponde OK, si autoelegge coordinatore. Altrimenti, attende che un nodo con ID più alto annunci la sua coordinazione.

Il coordinatore ha responsabilità speciali: monitorare la circolazione del token, condurre votazioni di consenso e rigenerare il token in caso di perdita.

election/election.service.ts 
async startElection(): Promise<void> {
  if (this.electionInProgress) return;
  this.electionInProgress = true;

  const higherNodes = this.getNodesWithHigherIds();

  if (higherNodes.length === 0) {
    // Nessun nodo con ID superiore
    await this.becomeCoordinator();
    return;
  }

  const responses = await Promise.allSettled(
    higherNodes.map((nodeId) =>
      this.sendElectionMessage(nodeId)
    )
  );

  const receivedOk = responses.some(
    (r) => r.status === 'fulfilled'
  );

  if (!receivedOk) {
    await this.becomeCoordinator();
  }
}

Tolleranza ai guasti

Il sistema gestisce tre scenari di failure:

  • Scenario A — Token perso: il nodo con il token crasha. Il coordinatore rileva l'assenza del token, conduce una votazione di consenso e rigenera un nuovo token con il saldo più recente.
  • Scenario B — Nodo non-token: un nodo senza token fallisce. Il ring viene ricostruito automaticamente escludendo il nodo guasto.
  • Scenario C — Recovery: un nodo ripristinato si annuncia al coordinatore e viene reintegrato nella topologia.
coordinator/coordinator.service.ts 
reconstructRing(): Map<number, number> {
  const topology = new Map<number, number>();

  for (let i = 0;
       i < this.activeNodes.length; i++) {
    const current = this.activeNodes[i];
    const next = this.activeNodes[
      (i + 1) % this.activeNodes.length
    ];
    topology.set(current, next);
  }

  return topology;
}
