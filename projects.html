PROGETTI

Due mondi molto diversi: una piattaforma enterprise con un pantheon di divinità, e un anello di bancomat che si passano un gettone.

<< TORNA ALLA MAPPA

WORLD 2-1 · MAIN QUESTASGARD

// piattaforma enterprise a microservizi — progetto privato, in produzione

Asgard è una piattaforma modulare che digitalizza la vita interna di un'organizzazione: aprire un ticket, chiedere un'approvazione, sapere chi ha in carico quale computer, trovare la procedura giusta senza chiedere al collega di fianco. È nata dentro un progetto di digital transformation nella sanità pubblica e oggi è in esercizio.

Dietro c'è un monorepo NestJS con dodici microservizi, un frontend Angular e circa trecento endpoint REST. Ogni servizio ha il suo database, il suo dominio e confini precisi. Non perché i microservizi siano di moda, ma perché il service desk e il motore di approvazioni hanno ritmi di evoluzione diversi, e tenerli nello stesso blocco significa fermare entrambi ogni volta che ne cambi uno.

Tutto gira su Azure Container Apps: un'unica immagine Docker multi-app da cui nascono dodici container che si differenziano per una sola variabile, Cosmos DB for MongoDB come database dei servizi, Azure SQL come warehouse analitico, Service Bus per gli eventi, Redis per realtime e rate limiting, Key Vault per i segreti. Sviluppo in locale con docker-compose, emulatore ufficiale del Service Bus incluso.

HTTP, QUANDO SERVE UNA RISPOSTA

Il frontend chiama ogni servizio direttamente, con il JWT dell'utente. Tra servizi, la chiamata sincrona si usa solo per domande che non possono aspettare: Gravos chiede a Heimdall chi è il manager del richiedente per risolvere un approvatore; Atlas chiede se un destinatario esiste ed è visibile a chi inoltra. Sono endpoint interni, mai raggiungibili dal browser.

EVENTI, PER CIÒ CHE PUÒ ASPETTARE

Tre code su Service Bus: log.create da tutti verso Bravon, send-email verso Deltor, search.index verso l'indice di ricerca. Se Deltor è fermo, i ticket si aprono lo stesso e le email partono quando torna su. In produzione i servizi si autenticano al bus con managed identity: nessuna connection string da custodire.

REALTIME, SENZA POLLING

Atlas espone un gateway Socket.IO con stanze per utente, gruppo e organizzazione. Quando un ticket viene creato, aggiornato o rilasciato, chi deve saperlo lo sa subito. L'adapter Redis fa sì che funzioni anche con più repliche dello stesso servizio, che non condividono memoria.

ATLAS · TICKETS.CONTROLLER.TS — RICOSTRUZIONE SEMPLIFICATA

// Apertura di un ticket. Ogni riga fa una cosa sola.
@Controller('tickets')
export class TicketsController {
  @Post()
  @Permissions(Permission.TicketCreate, Permission.TicketAll)
  async create(
    @ActiveUser() user: ActiveUserData,
    @Body() dto: CreateTicketDto,       // validato da class-validator
  ) {
    const ticket = await this.tickets.create(dto, user);

    // realtime: chi è nella stanza del gruppo destinatario lo vede subito
    this.gateway.to(`group:${ticket.destination}`).emit('ticket.created', ticket);

    // asincrono: mail e audit non devono rallentare la risposta
    this.bus.emit('send-email', { template: 'ticket-created', ticket });
    this.bus.emit('log.create',  { actor: user.sub, action: 'ticket.create', ref: ticket.id });

    return ticket;
  }
}

Il default è chiuso: su ogni servizio girano due guard globali, uno per l'autenticazione e uno per i permessi. Un endpoint pubblico va dichiarato esplicitamente, e nell'intera piattaforma l'unica scrittura senza login è la pagina di apertura ticket per chi non ha ancora un account: rate limit per IP, honeypot, consenso privacy obbligatorio e destinazione risolta lato server, così il form non può scegliere a chi arrivare.

IDENTITÀHEIMDALL, IL GUARDIANO

// un solo servizio sa chi sei. tutti gli altri si fidano della sua firma

DUE PORTE, UNA SOLA ANAGRAFICA

Si entra con l'account aziendale (Microsoft Entra ID) o con la carta d'identità elettronica (CIE id). In entrambi i casi: Authorization Code con PKCE S256, firma del token verificata via JWKS, controlli su issuer, audience, scadenza e nonce. Poi Heimdall emette i JWT interni della piattaforma: gli altri undici servizi validano quelli e non sanno nulla dell'identity provider.

REFRESH TOKEN A FAMIGLIE

Ogni refresh ruota il token e lo lega a una famiglia. Se un refresh token già consumato ricompare, qualcuno l'ha copiato: si revoca l'intera catena, non solo quel token, e il dispositivo legittimo rifà il login. Sugli endpoint di scambio il rate limit è volutamente ostile.

PERMESSI PER RISORSA

Ticket.Create, Asset.Read, Requests.Approve, Dashboard.Write: ogni servizio dichiara i permessi che accetta, Heimdall li assegna tramite gruppi funzionali e organizzazioni. Lo stesso elenco pilota il menu del frontend e i tool visibili all'assistente AI. La regola è scritta una volta e letta ovunque.

L'ANAGRAFICA SI AGGIORNA DA SOLA

Un job sincronizza il gestionale HR: valida i dipendenti, crea o aggiorna l'account su Entra ID e in Heimdall, assegna il manager, disabilita i cessati e invia un report con il CSV degli scarti. Gli endpoint interni consumati dagli altri servizi (manager di un utente, coordinatore di un gruppo, account ancora attivi) nascono tutti da qui. I dati personali nei log sono mascherati prima di partire.

WORKFLOWGRAVOS, LE APPROVAZIONI

// un modulo di richiesta si definisce con un documento, non con un deploy

Atlas gestisce i ticket; Gravos gestisce i processi: richieste che hanno un modulo, una catena di approvazioni e delle conseguenze. Un workflow è un documento con tre blocchi — fields (il form), steps (chi approva e come), actions (cosa succede dopo) — e viene agganciato a una sottocategoria di tipo richiesta del service desk: l'utente parte da «ho bisogno di» e il sistema decide se è un ticket o un workflow.

TRE MODI DI APPROVARE

SEQUENTIAL: A prima di B. PARALLEL: n membri di un gruppo, con un minimo di approvazioni. DYNAMIC: l'approvatore non è scritto nel workflow ma calcolato al momento — il manager del richiedente, il coordinatore del gruppo. Così un cambio di organigramma non richiede di toccare i processi.

AZIONI CON MEMORIA

Alla creazione, a ogni step, all'approvazione finale, al rifiuto o al completamento possono scattare azioni: assegnare un asset, inviare un'email, chiamare un'API. Ogni esecuzione viene registrata con input, output, esito e tentativi, e si può riprovare a mano se qualcosa a valle era giù.

API_CALL, MA NON OVUNQUE

Un'azione che chiama un'API è comoda e pericolosa: chi definisce i workflow potrebbe farla puntare dove vuole. Per questo il base URL deve appartenere a una allowlist configurata e il path viene sanificato — niente .., niente doppie barre, niente schemi. La flessibilità si concede, non si regala.

OTTO CONNETTORI, ZERO PASSWORD

Le credenziali di una sorgente non vengono mai salvate in chiaro: nel database c'è solo un secretRef, risolto a runtime da Key Vault o da variabili d'ambiente. Il test di connessione registra stato, latenza e ultimo errore, così una sorgente rotta si vede prima che un grafico resti vuoto.

UN DSL, NON SQL LIBERO

I pannelli non scrivono SQL: descrivono raggruppamenti, metriche, filtri e ordinamenti in un piccolo linguaggio che il motore traduce. È meno potente di una query a mano, ed è esattamente il punto: un errore di sintassi diventa un 400 con un suggerimento, non una tabella cancellata.

ANCHE LA PIATTAFORMA SI GUARDA

Lysor ospita la dashboard di stato del sistema: container, database, code e cache letti da Azure Monitor, più un probe /health per ogni servizio. Se Azure non risponde, restano i probe HTTP e l'ultimo inventario valido: la pagina degrada, non muore. Riservata a un ruolo che non dà accesso ai dati.

AIMIMIR, LA PORTA PER GLI LLM

// un assistente può usare la piattaforma. con i permessi di chi gli sta parlando, e non uno di più

Mimir è un server MCP (Model Context Protocol): espone i servizi esistenti come tool a un assistente esterno — Copilot, VS Code, Claude — o interno al portale. Non contiene logica di dominio e non ha un database: è un adattatore di protocollo. Ogni tool si traduce in una o più chiamate HTTP ai servizi, con il token dell'utente che sta chiedendo, e riusa validazione, permessi, audit, email e socket già implementati. Niente accesso diretto ai dati, mai.

MIMIR · FLUSSO DI AUTORIZZAZIONE (OAUTH 2.1)

  1. POST /mcp senza token                        -> Mimir:    401 + WWW-Authenticate (dov'è il resource metadata)
  2. GET  /.well-known/oauth-protected-resource   -> Mimir:    «l'authorization server è Heimdall» (RFC 9728)
  3. GET  /.well-known/oauth-authorization-server -> Heimdall: metadata del server (RFC 8414)
  4. POST /oauth/register                         -> Heimdall: registrazione dinamica del client (RFC 7591)
  5. GET  /oauth/authorize + PKCE                 -> Heimdall: redirect su Entra ID, poi code monouso (60 s)
  6. POST /oauth/token + code_verifier            -> Heimdall: JWT con claim mcpClientId, TTL breve
  7. POST /mcp + Bearer                           -> Mimir:    guard (app Mimir + Mcp.Access),
                                                               tool filtrati sui permessi dell'utente,
                                                               audit di ogni chiamata su Bravon

MIMIR · REGISTRAZIONE DI UN TOOL — RICOSTRUZIONE SEMPLIFICATA

registry.register({
  name: 'asgard_create_ticket',
  permissions: ['Ticket.Create', 'Ticket.All'],     // gli stessi di Atlas, nessuno nuovo
  input: z.object({
    category:    z.string(),
    subcategory: z.string(),
    subject:     z.string().min(5).max(240),
    description: z.string().min(10).max(5000),
  }),
  async run(input, user) {
    const sub = await categories.resolve(input, user.token);
    if (sub.type === 'richiesta') {
      return refuse('È un workflow: usa asgard_create_request');
    }
    // stessa chiamata che farebbe il frontend, stesso token, stessi side effect
    return upstream.post(atlas('/tickets'), { ...input, destination: sub.group }, user.token);
  },
});

VEDE SOLO CIÒ CHE PUOI

L'elenco dei tool viene filtrato sui permessi dell'utente prima di arrivare al modello: niente 403 evitabili, niente tentativi. Su una trentina di tool, le scritture sono quattro — aprire un ticket, avviare una richiesta, pubblicare una news o una FAQ. Nessuna modifica, nessuna cancellazione.

SI SA CHE C'ERA UN ROBOT

Un ticket aperto tramite assistente resta intestato all'utente, ma nasce con un commento di origine di tipo mcp — derivato dal claim nel token, non dal body che un client potrebbe scrivere a piacere. L'operatore vede un banner e sa che nessuno ha compilato il form a mano.

I TOKEN COSTANO

Ogni risposta viene proiettata in forma compatta: via gli id ridondanti, i campi di audit, gli embedding; elenchi con un tetto esplicito e testi troncati con una nota. È qui che si governa il costo di una conversazione — e il modello, con meno rumore, sbaglia meno.

DEPLOYDAL PUSH ALLA PRODUZIONE

// una pipeline a due stage, nessun segreto che la attraversa

UNA IMMAGINE, DODICI CONTAINER

Il monorepo compila tutte le app in una sola immagine; il comando di avvio è parametrico. Dodici container, una build da otto minuti invece di dodici build da venti. L'unica eccezione è Lysor, che si porta dietro il client Oracle e ha il suo Dockerfile.

I SEGRETI NON PASSANO DI QUI

La pipeline non conosce nessuna password. Le Container Apps leggono i segreti da Key Vault tramite una managed identity, e le variabili d'ambiente contengono solo un riferimento. Anche la build avviene sul registry remoto: l'agent non ha Docker, e non ne ha bisogno.

IN LOCALE COME IN PRODUZIONE

docker-compose up alza i dodici servizi con hot reload, l'emulatore ufficiale del Service Bus (che si porta dietro un SQL Server, perché così vuole Microsoft) e Redis. Le code sono dichiarate nello stesso file di configurazione che descrive quelle vere: un bug di messaging si riproduce sulla scrivania.

ASGARD IL NUCLEO

Planner, ricerca trasversale e note personali. Dà il nome all'intera suite. Perché: nella mitologia norrena è il regno degli dèi, il posto dove vivono tutti gli altri. Chiamare così una piattaforma gestionale è esattamente il livello di modestia che ti aspetti da chi sceglie i nomi alle undici di sera.

  • Planner con piani, bucket, obiettivi, task con dipendenze (e controllo anti-ciclo), vista Gantt e capacità per membro
  • Ricerca semantica su FAQ, news, documenti, procedure e workflow: embedding su Azure OpenAI, con fallback per parole chiave se non configurato
  • Consuma search.index / search.remove dagli altri servizi; propone quick action: «apri un ticket», «avvia questa richiesta»
ATLAS SERVICE DESK

Ticket, categorie, code e assegnazioni: il ciclo completo di una segnalazione. Perché: il titano che regge il peso del mondo — ma anche l'atlante, la raccolta di mappe. Regge il carico operativo e mappa ogni richiesta nella casella giusta. Il doppio senso è voluto.

  • Quattro stati (Nuovo · In carico · In attesa · Risolto), quattro priorità, commenti di tipo user / forward / system / mcp
  • Categorie a due livelli: la sottocategoria decide il gruppo destinatario, e se è di tipo richiesta reindirizza a Gravos
  • Rilascio automatico dei ticket presi in carico e dimenticati, con nota di sistema; gateway realtime; pagina pubblica per chi non ha ancora un account
BRAVON LOG & AUDIT

Registra chi ha fatto cosa e quando. Perché: è la scatola nera. Quando qualcosa va storto, Bravon sa già com'è andata e non ha la minima intenzione di coprirti.

  • Unico consumer della logger-queue: nessun servizio gli scrive via HTTP, quindi se è fermo gli altri non se ne accorgono
  • Espone un'API di consultazione per l'area amministrativa: filtri per attore, azione, servizio e periodo
  • Non maschera nulla, perché arriva già mascherato: email e codici fiscali vengono offuscati da chi produce il log
CORVIN COMUNICAZIONI

News e bacheca aziendale. Perché: i corvi di Odino, Huginn e Munin, volavano per il mondo e tornavano a riferirgli le notizie. Corvin fa lo stesso senza lasciare piume sulla scrivania.

  • News con testo formattato, copertina e allegati (caricati su Fayra), pubblicazione programmata
  • Visibilità per utente, gruppo o organizzazione, applicata dal servizio e non dal client
  • Salvataggio, feedback di utilità, notizie correlate; ogni contenuto finisce nell'indice di ricerca globale
DELTOR NOTIFICHE

Messaggi ed email generati da modelli riutilizzabili. Perché: dalla delivery, la consegna. È il servizio che ti scrive «la tua richiesta è stata approvata» e, ogni tanto, anche il contrario.

  • Template Handlebars per le email transazionali, inviate via SMTP e storicizzate una per una
  • Messaggi intranet in-app con stato letto / da leggere, opzionalmente inoltrati anche per email
  • Riceve quasi tutto via evento send-email: la logica di notifica non vive nei servizi che la scatenano
ELIOS KNOWLEDGE BASE

FAQ e procedure, organizzate e cercabili. Perché: Helios, il sole: fa luce. Esiste per farti trovare la risposta prima di aprire un ticket. Statisticamente non sempre riesce nell'intento.

  • FAQ categorizzate con ricerca full-text, conteggio delle visualizzazioni e tracciamento delle ricerche più frequenti
  • Ogni creazione, modifica o cancellazione emette un evento verso l'indice di ricerca di Asgard
  • Le ricerche senza risultato sono il miglior backlog per le prossime FAQ da scrivere
FAYRA DOCUMENTI

Archivio dei file e collegamenti con le altre entità. Perché: è l'archivio, il posto dove i documenti vanno a stare davvero — invece che in definitivo_v3_FINALE_ok.pdf sul desktop di qualcuno.

  • Quattro tipi in una libreria unica: documenti versionati con storico, procedure a passi, file binari, cartelle trasversali
  • Binari su Azure Blob Storage: container privato servito con URL firmati a scadenza, container pubblico per copertine e media
  • Ospita anche i CSV che Lysor usa come sorgenti dati, isolati dal resto della knowledge base
GRAVOS WORKFLOW

Moduli configurabili e approvazioni a più passaggi, anche in parallelo. Perché: gravitas. Qui si firma, si approva e si passa allo step successivo. È il servizio più serio della famiglia e lo sa.

  • Form builder con campi tipizzati e validazioni; richieste con stati PENDING → IN_PROGRESS → APPROVED / REJECTED → COMPLETED
  • Step sequenziali, paralleli con quorum, o dinamici (manager del richiedente, coordinatore del gruppo)
  • Azioni automatiche tracciate e riprovabili; template di azione riutilizzabili tra workflow
HEIMDALL IDENTITÀ & PERMESSI

Chi sei, in che gruppo stai, cosa puoi toccare. Perché: il guardiano del Bifröst, che vede a cento leghe e sente crescere l'erba. Se Heimdall dice di no, non entri: non c'è appello e non c'è «ma io sono il responsabile».

  • Login OAuth2/OIDC con Entra ID e CIE id; JWT interni con refresh token a rotazione e rilevamento del riuso
  • Utenti, gruppi, organizzazioni, permessi per risorsa; provisioning degli account su Entra ID via Graph
  • Fa anche da authorization server OAuth 2.1 per i client MCP di Mimir: registrazione dinamica, PKCE, token a vita breve
ITRIA INVENTARIO IT

Asset, sedi e indirizzi di rete. Perché: «IT» più un suffisso che suonasse mitologico. Sa quali macchine esistono, dove stanno e a chi sono in carico: le tre domande a cui in azienda nessuno sa mai rispondere.

  • Asset con ciclo di vita AVAILABLE → IN_USE → DISPOSED, categorie con campi custom, storico immutabile di ogni modifica, centri di costo
  • IPAM: VLAN, subnet gerarchiche con % di utilizzo, indirizzi IP con stato, MAC e hostname, rack a livello di unità
  • Sincronizzazione con il NAC di rete per scoprire host reali; controllo notturno degli asset rimasti assegnati a persone cessate
LYSOR DASHBOARD

Cruscotti e grafici costruiti su dati raccolti da fonti diverse. Perché: dal greco lýsis, sciogliere, scomporre. Prende numeri sparsi e li trasforma in grafici che qualcuno, prima o poi, metterà in una slide.

  • Otto connettori (HTTP, MySQL, PostgreSQL, SQL Server, Oracle, MariaDB, MongoDB, CSV), ingestor schedulati, dataset materializzati su Azure SQL
  • Tredici tipi di pannello, dal contatore al grafico misto; filtri di dashboard che si propagano ai pannelli via binding; export CSV
  • Permessi per singola dashboard; monitor di stato dell'infrastruttura riservato agli amministratori di sistema
MIMIR PONTE VERSO GLI LLM

Espone un insieme chiuso di strumenti agli assistenti AI, sempre con l'identità e i permessi di chi sta chiedendo. Perché: Odino conservava la testa di Mimir per consultarla quando gli serviva un consiglio. Io ho collegato un modello linguistico a una lista di strumenti sorvegliati. Concettualmente identico, sensibilmente meno truculento.

  • Server MCP con trasporto Streamable HTTP stateless: funziona con più repliche senza sessioni appiccicose
  • Una trentina di tool su knowledge base, news, ticket, richieste, asset e rete; input validato con zod; quattro sole scritture
  • Stessi tool anche come façade REST, per la futura chat interna al portale; audit di ogni chiamata con l'id del client

LEZIONICOSA MI HA INSEGNATO

CONFINI, NON STRATI

La domanda utile non è «dove metto questo codice», ma «di chi è questo problema». Un servizio che risponde a una sola domanda resta piccolo abbastanza da poterlo cambiare senza avere paura.

PARLARSI SENZA DIPENDERE

Le operazioni dirette vanno in chiamata sincrona; tutto ciò che può aspettare viaggia a eventi. Così una notifica lenta non rallenta chi ha aperto il ticket, e un servizio fermo non trascina giù gli altri.

IL BUS NON È UN TELEFONO

All'inizio anche le domande con risposta — «chi è il manager di X?» — passavano dal broker. Era comodo e sbagliato: un request/reply su una coda è più lento, più fragile e più difficile da proteggere di una chiamata HTTP interna. Le ho spostate. Il bus è rimasto per gli eventi, che è ciò per cui esiste.

I PERMESSI STANNO IN UN POSTO SOLO

La regola su chi può fare cosa vive in un servizio unico. Se la duplichi in dodici punti, prima o poi undici sono aggiornati e uno no — ed è sempre quello sbagliato.

DEGRADARE, NON CROLLARE

Senza Azure OpenAI la ricerca torna per parole chiave. Senza Azure Monitor restano i probe HTTP. Senza Redis lo state OAuth va su Mongo. Ogni dipendenza opzionale ha un piano B scritto prima che serva, perché quando serve non c'è tempo di scriverlo.

L'INTERFACCIA È METÀ DEL LAVORO

Uno strumento interno lo usano persone che non hanno scelto di usarlo. Se il flusso è confuso, non «si abitueranno»: torneranno a mandarti email. La UI qui non è la rifinitura, è il requisito. Il case study della dashboard racconta come.

WORLD 2-2 · SIDE QUESTTOKEN RING

// sistema bancario distribuito — progetto universitario, codice pubblico

Quattro sportelli bancomat indipendenti condividono lo stesso conto corrente. Non hanno memoria in comune e nessuno fa da capo: devono mettersi d'accordo solo scambiandosi messaggi.

La soluzione è l'algoritmo Token Ring: un unico gettone gira nell'anello e porta con sé il saldo. Chi ha il gettone può operare, tutti gli altri aspettano. È la mutua esclusione ottenuta senza lock e senza semafori — e soprattutto senza race condition, perché due nodi non possono proprio toccare il saldo nello stesso momento.

Ogni nodo è un processo NestJS separato che conosce solo il proprio successore; il gettone viaggia come una POST HTTP. Sopra l'anello c'è un coordinatore eletto con il Bully Algorithm, che interviene solo quando qualcosa si rompe: rigenera il gettone se si perde, ricostruisce l'anello se un nodo cade, reintegra chi torna.

IL GETTONE

Il token è una struttura minuscola: un identificativo univoco, il nodo che lo detiene e il saldo. Tutta la correttezza del sistema sta in quel terzo campo — il saldo non è replicato da nessuna parte, esiste solo dentro il gettone che sta girando.

SEZIONE CRITICA

Quando il gettone arriva, il nodo guarda se ha transazioni in coda. Se sì entra nella sezione critica, esegue una transazione, aggiorna il saldo nel token e lo passa avanti. Se no, lo inoltra subito: tenere fermo il gettone significa bloccare tutti gli altri. Una transazione per giro, così nessun nodo può monopolizzare il conto.

IL SALDO NON STA DA NESSUNA PARTE

Il servizio bancario è fatto di funzioni pure: riceve il saldo dal token, restituisce il saldo nuovo, non conserva niente. Prelievo oltre la disponibilità? Un'eccezione, e il saldo nel gettone resta quello di prima. È l'unico modo per rispettare il vincolo «nessuna memoria condivisa» senza barare.

SRC/ATM/ATM.SERVICE.TS — processToken()

private async processToken(): Promise<void> {
  this.isProcessing = true;
  try {
    if (this.tokenService.canAccessCriticalSection()) {
      // Has pending transactions: execute one transaction
      await this.executeNextTransaction();
    } else {
      // No pending transactions: brief display delay, then forward immediately
      // (In production, this delay should be 0 - token should be forwarded immediately)
      if (TOKEN_DISPLAY_DELAY > 0) {
        this.logger.info(
          `No pending transactions. Holding token for ${TOKEN_DISPLAY_DELAY}ms (display only)...`,
        );
        await new Promise((resolve) => setTimeout(resolve, TOKEN_DISPLAY_DELAY));
      }
      await this.forwardToken();
    }
  } finally {
    this.isProcessing = false;
  }
}

Sul ritardo di cinque secondi: non fa parte dell'algoritmo. Senza, il gettone fa il giro dell'anello in pochi millisecondi e in una presentazione non si vede niente. È una costante, è documentata come «solo per la demo», e in produzione vale zero. Barare in modo dichiarato è comunque non barare.

SRC/BANKING/BANKING.SERVICE.TS — withdraw()

withdraw(currentBalance: number, amount: number): number {
  if (amount <= 0) {
    throw new Error('Withdrawal amount must be positive');
  }
  if (currentBalance < amount) {
    throw new Error(
      `Insufficient funds. Current balance: ${currentBalance}, requested: ${amount}`,
    );
  }
  return currentBalance - amount;   // nessuno stato: il saldo entra ed esce
}

IL BULLY ALGORITHM

Quando un nodo sospetta che il coordinatore sia morto, manda ELECTION a tutti quelli con id più alto. Se qualcuno risponde OK, si fa da parte e aspetta l'annuncio; se nessuno risponde entro il timeout, si proclama coordinatore e lo comunica a tutti quelli con id più basso. Vince sempre l'id più alto ancora vivo. Il nome dell'algoritmo è letteralmente «il bullo», perché il nodo più grosso zittisce gli altri. Non l'ho scelto io.

SRC/ELECTION/ELECTION.SERVICE.TS — startElection(), condensato

async startElection(): Promise<void> {
  if (this.electionInProgress) return;      // una alla volta
  this.electionInProgress = true;

  const higherNodes = this.getNodesWithHigherIds();
  if (higherNodes.length === 0) {
    await this.becomeCoordinator();          // nessuno sopra di me: comando io
    return;
  }

  const responses = await Promise.allSettled(
    higherNodes.map((id) => this.sendElectionMessage(id, { type: 'ELECTION', senderId: this.nodeId })),
  );
  const receivedOk = responses.some((r) => r.status === 'fulfilled' && r.value === true);

  if (receivedOk) {
    // qualcuno più grosso è vivo: aspetto il suo COORDINATOR, altrimenti riprovo
    this.coordinatorTimeoutHandle = setTimeout(() => {
      this.electionInProgress = false;
      this.startElection();
    }, COORDINATOR_TIMEOUT);
  } else {
    await this.becomeCoordinator();
  }
}

A · IL GETTONE È PERSO

Il nodo che lo aveva è crollato con il saldo in tasca. Ogni nodo tiene un lastTokenSeen e ogni 5 secondi controlla: se sono passati più di 30 senza vedere il gettone, lo dichiara perso e avvia un'elezione. Il coordinatore non rigenera subito: prima indice un voto.

B · UN NODO CADE, SENZA GETTONE

Il predecessore prova a consegnare: 5 tentativi a 2 secondi, poi marca il successore come FAILED. Se è il coordinatore, ricostruisce l'anello saltando il morto e manda la nuova topologia a tutti; se non lo è, avvia un'elezione. Il gettone continua a girare, con un nodo in meno.

C · UN NODO TORNA

Al riavvio il nodo annuncia il rientro al coordinatore, che verifica la sua salute e lo reinserisce nell'anello. Se ha ancora un vecchio gettone in memoria, lo butta: accetta solo il token con l'id che il coordinatore gli comunica nella topologia.

IL PROBLEMA DEL DOPPIO GETTONE

Il bug più subdolo di un token ring non è perdere il gettone: è ritrovarsi con due. Succede se più nodi rilevano la perdita nello stesso istante e ognuno ne rigenera uno; o se un nodo «morto» era in realtà solo lento e riappare con il vecchio token. Due gettoni significano due saldi, e a quel punto la banca ha un problema serio. La difesa è in quattro mosse:

  1. Una sola elezione. Chi rileva la perdita non decide: avvia il Bully, e decide solo chi lo vince.
  2. Voto di consenso. Il coordinatore chiede a ogni nodo attivo: hai il token? quale id? che saldo? Se anche uno solo ce l'ha, non era perso — era lento. Nessuna rigenerazione.
  3. Invalidazione prima della nascita. Se nessuno ce l'ha, il coordinatore manda INVALIDATE_TOKEN: tutti scartano qualunque gettone e rifiutano qualsiasi token in arrivo finché non conoscono il nuovo id.
  4. Un id solo è valido. Il token rigenerato ha un UUID nuovo e il saldo più alto tra quelli votati; l'id viaggia nella topologia e ogni nodo accetta solo quello. Un vecchio gettone che riappare viene ignorato.

// ogni nodo risponde al coordinatore con la verità, non con un'opinione
voteTokenStatus(request: TokenStatusVoteRequest): TokenStatusVoteResponse {
  const token = this.tokenService.getToken();
  return {
    nodeId: this.nodeId,
    hasToken: token !== null,
    tokenId: token?.id ?? null,
    balance: token?.balance ?? null,
    timestamp: new Date(),

// ...e il coordinatore decide sulla base dei voti
const votes = await this.conductTokenStatusVote();
const nodesWithToken = votes.filter((v) => v.hasToken);

if (nodesWithToken.length > 0) {
  // SCENARIO B: qualcuno ce l'ha. Era lento, non perso. Non si tocca niente.
  this.startTokenCirculationMonitor();
} else {
  // SCENARIO A: perso davvero. Prima si invalida, poi si rigenera.
  await this.broadcastInvalidateToken('Token lost, regenerating new token');

  let maxBalance = this.lastKnownBalance;
  for (const vote of votes) {
    if (vote.balance !== null && vote.balance > maxBalance) maxBalance = vote.balance;
  }

  const regenerated = this.coordinatorService.regenerateToken(uuidv4(), maxBalance);
  this.tokenService.receiveToken(regenerated);
  await this.coordinatorService.broadcastTopology(this.coordinatorService.reconstructRing());
  await this.processToken();          // e si riparte
}

SRC/COORDINATOR/COORDINATOR.SERVICE.TS — reconstructRing()

reconstructRing(): Map<number, number> {
  if (!this.isCoordinator) {
    throw new Error('Only coordinator can reconstruct ring');
  }
  const topology = new Map<number, number>();

  // For each active node, find the next active node (circular)
  for (let i = 0; i < this.activeNodes.length; i++) {
    const currentNode = this.activeNodes[i];
    const nextNode = this.activeNodes[(i + 1) % this.activeNodes.length];
    topology.set(currentNode, nextNode);
    this.logger.info(`ATM${currentNode} -> ATM${nextNode}`);
  }
  return topology;
}
